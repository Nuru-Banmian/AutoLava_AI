# Phase 3：单门店只读 Agent 查询与经营分析

## Problem Statement

AutoLava AI 已经能够记录单门店的每日台账、动态收入分类、其他数据、记录天气、营业状态、洗车数量和公司结算，但经营人员仍需进入不同页面、选择时间范围并自行组合指标，才能回答“本月收入是多少”“为什么比上月低”“哪些分类发生了变化”等自然语言问题。

历史 Phase 3 提案把查询能力固化为较多固定意图，并混入跨门店分析、Agent 写操作、审批提案和已经失效的模型名称。它没有充分适配当前 SQLite、单 Uvicorn worker、2‑GB 服务器、动态收入分类、公司结算口径和现有首页布局，也没有形成统一且可复核的经营证据合同。

用户需要的是一个位于首页、面向当前选定门店的只读 Agent：用户可以灵活提问，模型负责理解和组织回答，后端负责权限、日期、指标、比较、完整性和金额计算。Agent 必须能够解释证据限制，但不能生成 SQL、扩大门店范围、把缺失数据当作零、编造金额、作出因果断言或执行经营写入。

首个发布切片只开放给管理员和最终管理员。门店记忆已经明确延期，不属于本规格。

## Solution

在首页三个简报卡片下方增加一个单门店只读 Agent 对话区。管理员和最终管理员可以针对当前选定门店提出经营查询和经营分析问题；普通用户看不到 Agent，也不能调用 Agent 路由。

每轮由模型先产生受限、结构化的 TurnPlan。信息不足时追问并结束本轮；无需取证时直接回答；需要经营事实时一次提交 EvidencePlan。后端把 EvidencePlan 当作不可信输入，通过唯一的批量取证 Interface 校验权限、当前门店、门店时区、日期、指标、分组、过滤和调用上限，并在同一个 SQLite 只读快照内完成整批取证，返回统一 EvidenceBundle。模型只能读取后端计算完成的结构化证据并组织回答。

运行流程使用 LangChain 与浅层 LangGraph，但 LangGraph 只负责有限的单轮流程控制，不使用开放式 ReAct Tool 循环、产品级 checkpoint、interrupt、LangGraph Server 或独立 Agent 容器。会话、结构化会话状态、消息和原始 Tool 证据由 AutoLava 自己持久化。

当前对话在页面刷新、跳转和重新进入系统后恢复。模型每轮只加载结构化会话状态、最近对话窗口、常驻规则、Skills 和 Tool 说明，不反复发送完整历史或旧 Tool 证据。只有用户主动确认“重置会话”后，系统才永久删除该用户在该门店的当前聊天正文、结构化状态和原始 Tool 证据。

最终回答完整生成并通过后端校验后一次性显示。页面可以显示“正在理解问题”“正在查询数据”“正在整理回答”等阶段状态，但不逐 Token 展示半成品。需要查看大量每日记录时，回答可以附带经过后端验证的“查看营业记录”操作，用户点击后才跳转并预填月份范围。

## User Stories

1. As an 管理员, I want to 在首页询问当前门店的经营数据, so that 我无需手工组合多个页面和指标。
2. As an 最终管理员, I want to 使用与管理员相同的单门店 Agent 能力, so that 最高权限身份不会反而失去经营查询能力。
3. As an 普通用户, I want to 不看到尚未向我开放的 Agent, so that 产品不会展示不可用入口或产生模型费用。
4. As an 最终管理员, I want to 控制 Agent 的全局启用状态, so that 原型验证或供应商故障时可以安全关闭 Agent 而不影响现有业务功能。
5. As an 管理员, I want to 只能查询当前选定门店, so that 一次对话不会意外混入其他门店数据。
6. As an 管理员, I want to 在需要其他门店数据时先切换门店, so that 门店范围始终由界面和后端权限决定。
7. As an 管理员, I want to 用自然语言灵活提问, so that 我不受固定问句模板限制。
8. As an 管理员, I want to 在未指定时间时默认查询本月截至今天, so that 简单问题可以立即得到有明确日期的回答。
9. As an 管理员, I want to 在使用“最近”“前段时间”等含糊期间时收到追问, so that Agent 不会擅自猜测日期。
10. As an 管理员, I want to 清楚区分“上月”和“上月同期”, so that 完整自然月不会被暗中替换成等长期间。
11. As an 管理员, I want to 查询指定日期、自然月、自然年或自定义期间, so that 不同经营问题都能使用准确范围。
12. As an 管理员, I want to 在比较非等长期间时先看到数值和金额差, so that Agent 不会用误导性的百分比替代事实。
13. As an 管理员, I want to 只在明确询问时获得非等长期间百分比, so that 比较口径保持可理解。
14. As an 管理员, I want to 在基准值为零时看到百分比不可用, so that Agent 不产生无意义或无限大的变化率。
15. As an 管理员, I want to 查询本月收入, so that 我可以得到每日台账营业额与已确认公司结算收入组成的月度总收入。
16. As an 管理员, I want to 查询每日台账营业额, so that 我可以单独理解日常经营表现。
17. As an 管理员, I want to 查询已确认公司结算收入, so that 我可以区分公司结算对月份总额的贡献。
18. As an 管理员, I want to 查询经营日数量, so that 休息日不会被当作正常经营样本。
19. As an 管理员, I want to 把营业和提前休息都计为经营日, so that 提前休息当天产生的经营事实不会被排除。
20. As an 管理员, I want to 查询经营日均台账营业额, so that 我可以在不混入公司结算的情况下理解日常经营表现。
21. As an 管理员, I want to 查询月度日均收入, so that 我可以按月理解月度总收入与经营日之间的关系。
22. As an 管理员, I want to 在门店启用记录洗车数量时查询洗车数量, so that 我可以结合业务量理解营业额。
23. As an 管理员, I want to 在洗车数量覆盖不完整时看到覆盖范围, so that 缺失值不会被当作零。
24. As an 管理员, I want to 查询平均每车收入, so that 我可以得到同时记录洗车数量的经营日中每日台账营业额除以洗车数量的结果。
25. As an 管理员, I want to 查询动态收入分类金额, so that 历史分类名称和当前配置都能按其保存时的口径正确统计。
26. As an 管理员, I want to 查询其他数据金额, so that 不计入总营业额的分类数据不会与收入混淆。
27. As an 管理员, I want to 按日期、自然月、自然年、收入分类、记录天气、星期或营业状态分组, so that 我可以从不同经营维度查看一个主要指标。
28. As an 管理员, I want to 按收入分类、记录天气、星期和营业状态进行确定性过滤, so that 组合查询仍然保持受限和可复核。
29. As an 管理员, I want to 在分类名称找不到时看到可选分类, so that Agent 不会模糊匹配或猜测相似名称。
30. As an 管理员, I want to 查询最高或最低每日台账营业额, so that 只比较经营日并保留所有并列结果。
31. As an 管理员, I want to 把零收入经营日视为有效经营日数据, so that 最低值不会因为金额为零而被静默移除。
32. As an 管理员, I want to 查询某一天的每日台账, so that 我可以看到该日金额、分类、记录天气、营业状态、洗车数量和原始事件。
33. As an 管理员, I want to 只在单日查询中看到原始事件, so that 自由文本不会被模型当作跨记录规律或因果证据。
34. As an 管理员, I want to 查询未记录日期, so that 我可以识别所选范围内缺少每日台账的日期而不推断门店本应营业。
35. As an 管理员, I want to 查询记录天气和洗车数量缺失情况, so that 分析结论可以披露数据覆盖限制。
36. As an 管理员, I want to 检查分类记账合计不一致, so that 受损数据不会支撑错误结论。
37. As an 管理员, I want to 在公司结算功能启用时查询结算公司和开票记录, so that 我可以了解待到账、已确认和公司维度的金额。
38. As an 管理员, I want to 在公司结算功能关闭时仍让历史已确认金额进入月度总收入, so that 关闭功能不会改写历史经营口径。
39. As an 管理员, I want to 在公司结算功能关闭时不能查询详细开票记录, so that Agent 遵守现有功能开关与权限规则。
40. As an 最终管理员, I want to 在已启用公司结算的当前门店看到与管理员一致的公司结算入口和数据, so that 最终管理员权限不会错误丢失业务内容。
41. As an 管理员, I want to 询问为什么收入发生变化, so that Agent 可以先复现总收入变化再解释可验证的组成。
42. As an 管理员, I want to 把总收入变化精确拆成每日台账营业额变化和已确认公司结算收入变化, so that 解释可以与总额对账。
43. As an 管理员, I want to 把每日台账营业额变化分解为经营日数量和经营日均台账营业额贡献, so that 我可以区分经营天数和日常表现。
44. As an 管理员, I want to 在分解中避免计算顺序偏置, so that 两个贡献项使用对称且可复现的方法。
45. As an 管理员, I want to 在证据充分时看到“主要来自”某项贡献, so that 结论具有明确且由后端验证的依据。
46. As an 管理员, I want to 在证据不足时看到“多个因素共同构成”或“尚未解释”, so that 模型不会为了完整故事而编造原因。
47. As an 管理员, I want to 把收入分类和其他数据用于精确金额分解, so that 计入与不计入总额的项目保持各自口径。
48. As an 管理员, I want to 只在洗车数量覆盖充分时使用洗车数量和平均每车收入解释, so that 稀疏数据不会造成错误归因。
49. As an 管理员, I want to 把记录天气和星期只作为相关现象, so that Agent 不把观察性差异表述为因果结论。
50. As an 管理员, I want to 在完整对账后停止无关探索, so that 回答保持聚焦并减少模型与数据库成本。
51. As an 管理员, I want to 首先看到直接答案, so that 我无需阅读内部过程才能得到结果。
52. As an 管理员, I want to 在答案中看到准确期间、口径、证据和限制, so that 我可以复核 Agent 的结论。
53. As an 管理员, I want to 看到安全可读的证据摘要而不是原始 Tool JSON, so that 信息透明但不会暴露内部结构或造成阅读负担。
54. As an 管理员, I want to 在请求大量每日记录时看到“查看营业记录”按钮, so that 聊天不会输出数百行数据。
55. As an 管理员, I want to 点击按钮后才跳转并预填开始月份和结束月份, so that 模型不能主动导航或生成任意 URL。
56. As an 管理员, I want to 在页面刷新、跳转和重新进入后恢复完整当前对话, so that 查询过程不会因导航丢失。
57. As an 管理员, I want to 在不同用户和不同门店之间隔离对话, so that 任何聊天和证据都不会串门店或串账号。
58. As an 管理员, I want to 主动重置会话, so that 新问题可以从干净上下文开始。
59. As an 管理员, I want to 在永久删除会话前看到不可恢复确认, so that 聊天正文和证据不会被误删。
60. As an 管理员, I want to 在发送问题后看到理解、查询和整理阶段状态, so that 我知道请求仍在处理。
61. As an 管理员, I want to 只看到完整生成的最终回答, so that 中途失败不会留下半句话或半截数值。
62. As an 管理员, I want to 在模型或数据库暂时失败时看到脱敏重试提示, so that 错误信息不会泄露密钥、SQL、提示词或内部数据。
63. As an 最终管理员, I want to 查看不含聊天内容的模型运行统计, so that 我可以评估供应商、模型、Token、延迟、结果和估算费用。
64. As an 最终管理员, I want to 在供应商配置错误或总体预算接近上限时收到脱敏告警, so that 我可以恢复服务而不读取用户聊天内容。
65. As an 维护者, I want to 用假的 Model Adapter 运行完整 Agent HTTP 测试, so that CI 不调用付费模型且仍能验证真实权限、数据库、取证和编排。
66. As an 维护者, I want to 在发布前验证 2‑GB 服务器的峰值内存、延迟、并发、模型费用和 SQLite 快照行为, so that Agent 不会拖垮现有业务。
67. As an 维护者, I want to 让任何跨门店泄露、金额错误、证据编造或提示注入绕过都阻止发布, so that 安全和数值正确性保持零容忍。

## Implementation Decisions

- 首版只开放给 `admin` 角色，包括管理员和最终管理员。普通用户看不到 Agent UI，调用后端 Agent 路由返回拒绝。最终管理员可以控制 Agent 的全局启用状态；关闭 Agent 不影响现有记账、营业记录、公司结算和经营分析页面。
- Agent 永远绑定当前选定门店。后端从已认证用户、路由中的当前门店和实时授权关系建立 RuntimeContext；模型不能填写或覆盖用户 ID、门店 ID、角色、成员关系、门店时区或功能开关。
- 权限、门店范围、Tool 白名单、参数类型、指标计算和调用上限属于后端硬约束。常驻核心规则优先于 Skills；Skills 优先于用户输入和经营数据。事件文本、分类名称和模型输出都视为不可信数据。
- 首版全部经营查询、经营分析和公司结算说明 Skills 每轮常驻加载，全部当前 Tool 说明每轮提供给模型。不实现动态 Skill 路由、`load_skill` Tool 或多层 Skill 选择。
- 模型只接触经营分析所需事实：每日台账、动态收入分类历史快照、其他数据、启用时的洗车数量、记录天气、星期、营业状态，以及必要的公司结算经营数据。账号、密码、成员关系、门店地址和坐标、创建人/修改人、内部日志、备份、告警、数据库结构和 SQL 不进入模型上下文。
- 采用一个深 Module `BusinessEvidenceCollector`，对外只有一次批量收集经营证据的 Interface。调用者提交 EvidencePlan 与 RuntimeContext，Module 返回 EvidenceBundle；模型不直接调用内部经营 Module。
- Collector 内部保留四类深 Module：通用经营指标查询、单日每日台账读取、公司结算明细查询和数据完整性检查。LangChain Adapter 只是普通 Python/Pydantic Interface 的薄 Adapter；LangGraph 不承担指标计算、权限或事务细节。
- EvidencePlan 每个子请求只包含一个主要指标和至多一个分组维度，并可包含多个受限、确定性的过滤条件。模型不能提交 SQL、表名、字段名、表达式、URL、门店 ID、用户 ID 或任意路由参数。
- 指标白名单包含：月度总收入、每日台账营业额、已确认公司结算收入、经营日、经营日均台账营业额、月度日均收入、洗车数量、平均每车收入、收入分类金额和其他数据金额。
- 分组白名单包含：日期、自然月、自然年、收入分类、记录天气、星期和营业状态。事件、用户、门店、地址和创建人不能成为分组维度。
- 过滤白名单包含：收入分类、记录天气、星期和营业状态。同一字段多个值为任一匹配，不同字段之间为同时满足。分类名称只做首尾空格、大小写等确定性规范化；找不到时返回可选分类，不进行模糊猜测。
- 所有查询使用受限期间对象。允许当前月、上一个自然月、上月同期、指定自然月、指定自然年、准确日期和自定义日期范围。期间由后端按当前门店时区解析，模型不能传时区或改变解析结果。
- 完全省略期间时默认当前门店本月 1 日至今天，并在回答中显示准确起止日期。“最近”“前段时间”等含糊表达必须追问。
- “上月”始终是完整上一个自然月；“上月同期”才是相同日号范围。非等长期间默认提供数值与金额差；只有用户明确询问时才计算百分比，并提示非等长。基准为零时百分比不可用。
- 经营分析未指定比较基准时默认“本月截至今天 vs 完整上月”；没有历史数据时只描述当前期间。不进行月底外推、未来收入预测或百分比预测。
- `经营日`必须包含营业和提前休息，排除休息。实现时修复现有分析中只把营业计入经营日、但分子包含提前休息营业额的不一致，并补充回归测试。
- 平均每车收入只使用同时记录洗车数量的经营日，以每日台账营业额合计除以洗车数量合计，不包含公司结算。关闭记录洗车数量、覆盖不足或洗车数量合计为零时返回不可用或限制说明，缺失不能当作零。
- 月度总收入等于该月每日台账营业额加该月已确认公司结算收入。公司结算按开票月份整笔归属，没有日粒度；查询区间只要与开票月份重叠，就纳入该月整笔已确认金额。
- 普通收入查询直接使用月度总收入，不读取公司结算明细。只有用户明确询问开票记录、结算公司、待到账、已确认或某公司金额时才使用明细能力。功能关闭时详细查询保持拒绝，但历史已确认金额继续计入月度总收入。
- 实现 Agent 时同时复现并修复“最终管理员在已启用公司结算的门店看不到普通用户和管理员可见的公司结算/开票内容”问题。以同一个已启用门店下普通用户、管理员、最终管理员三种身份验证入口、页面和开票记录。
- 数据完整性证据包括：所选范围未记录日期、缺少记录天气、启用记录洗车数量时的缺失和覆盖率、分类记账合计不一致。未记录日期只表示没有每日台账，不推断门店是否应该营业，也不推断记录起始日期。
- 最高/最低每日台账营业额默认只比较经营日，零收入经营日仍是有效值，并列值全部返回。
- 事件只在读取某一日每日台账时原样返回。首版不按事件搜索、筛选、分组或分析。门店记忆、经营观察和事件分类全部延期。
- 所有经营 Tool 返回统一 EvidenceBundle 外壳，包含执行状态、`current_store` 范围标识、后端解析后的准确日期、指标名称、单位、计算版本、后端计算结果、覆盖信息、后端计算的比较结果、未记录/缺失/非等长/零基准警告和截断状态。
- 用户只看到安全可读的证据摘要，不直接看到原始 Tool JSON。原始 EvidenceBundle 保存到当前会话，供后端复核，直到用户重置会话。
- 正常情况模型一次生成 EvidencePlan。后端在查询前预校验；仅对可修正的格式、枚举或结构错误提供机器可读反馈并允许模型修正一次。权限、门店范围、白名单和安全拒绝不能通过修正、重试或切换模型绕过。用户期间含糊或分类无法确定时必须追问。
- Collector 在一个 SQLite 只读快照中执行整批子查询。外部模型调用必须发生在 SQLite 事务和写锁之外。明确的临时 SQLite 故障可以关闭当前快照，并在新快照中整批自动重试一次；禁止只重试某个子查询并混合不同快照。未知技术错误或第二次失败时整批证据作废。
- 首版 LangGraph 是固定、浅层、串行且有调用上限的单轮流程：读取最近对话与结构化会话状态；生成 TurnPlan；追问、直接回答或一次批量取证；最多一次例外补充取证；生成完整回答或安全失败。
- 不使用开放式 ReAct Tool 循环、LangGraph interrupt、产品级 checkpoint、LangGraph Server、LangSmith 强依赖或独立 Agent 容器。LangGraph 只持有当前单轮的 route、EvidencePlan、EvidenceBundle、是否已补充、最终回答、白名单页面操作和脱敏失败状态。
- 每个用户、每个门店同时只有一个当前对话。AutoLava 持久化完整用户消息、完整 Agent 回答、结构化会话状态和原始 Tool 证据；刷新页面、跳转页面或之后返回时恢复完整当前对话。
- 模型每轮加载结构化会话状态与最近对话窗口，不加载完整历史。结构化状态保存已确认期间、指标、过滤、比较对象和待澄清事项。旧 Tool 证据不自动跨轮重新发送给模型。
- 新的金额、比较、排名、覆盖率或分析问题必须重新取证。仅复述或解释上一条回答时可以参考已有回答文本，不复用旧证据冒充新事实。
- 首版没有小时级自动过期。只有用户点击“重置会话”并通过不可恢复确认后，才永久删除当前聊天正文、结构化状态和全部 Tool 证据。模型和后台任务不能自行轮换、清空或提前删除当前对话。
- 可以保留不含聊天内容的运行统计，包括角色、供应商、模型、输入/输出 Token、结果、错误类别、延迟和估算费用。重置会话不删除这类统计。
- 经营分析先复现月度总收入变化，再精确拆为每日台账营业额变化和已确认公司结算收入变化。随后使用经营日与经营日均台账营业额分析每日台账变化，再检查计入总额的动态收入分类、其他数据和覆盖充分的洗车数量。
- 每日台账营业额变化采用对称分解，避免先算经营日还是先算经营日均造成顺序偏置：经营日数量贡献使用经营日差乘两个期间经营日均台账营业额的平均值；经营日均贡献使用经营日均差乘两个期间经营日数量的平均值。两个贡献之和必须精确复现每日台账营业额变化。
- 任一期间没有经营日或关键覆盖不足时不强行分解。证据充分性由后端计算，模型只能按后端状态组织措辞。默认只有最大已验证贡献达到全部绝对贡献的 60% 且关键数据完整时才允许使用“主要来自”；否则使用“多个因素共同构成”或说明尚未解释。该阈值作为后端可配置规则，而不是写入提示词。
- 最终发现分为“已验证”“相关现象”“尚未解释”。已验证结论必须通过金额分解对账；记录天气、星期和洗车数量只能作为相关现象，不能补齐未解释金额或断言因果。精确对账完成后停止无关探索。
- 最终回答包含直接答案、关键证据、准确期间与指标口径、覆盖/限制以及可选白名单页面操作。回答不强制使用固定报表版式，但必须优先回答用户实际问题。
- 大量指定期间每日记录可以返回 `open_business_records` 类型的白名单页面操作，只包含开始月份和结束月份。后端校验操作类型和月份范围；模型不能生成 URL 或门店 ID。前端显示“查看营业记录”，只有用户点击才使用当前选定门店跳转并预填营业记录范围。
- 首页 Agent 位于三个简报卡片下方。桌面端使用卡片下方宽空间，移动端在卡片后自然纵向排列。不新增独立 Agent 页面或导航项。
- 页面显示理解、查询和整理阶段状态。最终回答完整生成后一次性显示，白名单页面操作随完整回答返回；首版不逐 Token 流式输出，不在聊天中保留半截回答。
- 模型供应商通过统一 Model Interface 和供应商 profile 隔离。候选为 DeepSeek 官方 API、阿里云百炼和硅基流动，但本规格不选择具体模型、主供应商或备用供应商。业务代码不能硬编码供应商或模型名。
- 生产 Adapter 使用 OpenAI-compatible 核心传输，但 profile 分别处理 base URL、模型 ID、结构化输出方式、思考参数、错误映射和响应差异。模型与接口行为必须在原型阶段按供应商最新官方文档验证，不能使用历史失效模型名。
- API Key 只能位于被 Git 忽略的根目录 `.env` 或部署 Secret。真实密钥不能进入聊天、Git、前端、日志、错误响应或 `.env.example`；`.env.example` 只记录变量名和安全说明。
- 临时网络故障、超时、429 或供应商 5xx：当前模型最多重试一次；仍失败且配置备用模型时，完整重做当前模型阶段一次。API Key 无效、余额不足、模型名或参数错误不盲目重试，而是生成最终管理员可见的脱敏配置告警。内容安全拒绝、权限拒绝和用户信息不足不能通过切换供应商绕过。
- 提示注入防护采用关闭式失败。用户输入、事件文本、分类名称、结算公司名称和 Tool 证据只能作为数据，不能覆盖系统规则。任何无法安全验证的计划、证据或回答都拒绝、追问或返回数据不足，不能猜测后继续。
- 管理告警和普通日志不保存 API Key、系统提示、用户原始问题、Agent 回答全文、原始 Tool JSON、SQL 或直接个人联系/支付标识。诊断使用会话/运行标识、阶段、供应商、模型、错误类别、耗时和脱敏摘要。
- 发布先由最终管理员受控启用，只向管理员和最终管理员开放。2‑GB 服务器是否足够由资源原型决定；实现应优先控制内存，不预先承诺升级。若实测没有安全余量，则阻止发布并重新评估优化或服务器资源，而不是在同一台 2‑GB 机器上拆分额外容器冒充节省内存。

## Testing Decisions

- 主要后端验收 seam 是管理员向当前门店 Agent 发送消息的 HTTP Interface。测试使用 Fake Model Adapter，但运行真实认证授权、SQLite、会话持久化、BusinessEvidenceCollector、浅层 LangGraph 和响应序列化。
- 测试只断言用户可见响应、持久化结果、业务数值、权限结果和外部错误模式，不绑定 LangGraph 节点名称、提示词内部文本、SQL 形状或 Module 私有协作方式。
- Model Interface 必须至少有生产 OpenAI-compatible Adapter 与测试 Fake Adapter，因此这是一个真实 seam。测试 Fake 可以依次返回追问、直接回答、合法 EvidencePlan、非法计划、补充计划、供应商超时和最终回答。
- 通过 HTTP seam 覆盖管理员与最终管理员成功访问、普通用户 403、停用用户 401、未授权/不存在门店不可见、当前门店硬隔离以及模型无法注入门店 ID。
- 通过 HTTP seam 覆盖每个受限期间对象、门店时区、月末和跨年、闰年、上月与上月同期、非等长期间、零基准及含糊期间追问。
- 通过 HTTP seam 验证全部指标、允许的分组和过滤、动态分类规范化、未知分类候选、洗车数量开关与覆盖、公司结算开关、已确认历史收入、并列极值和零收入经营日。
- 对月度总收入建立金标准测试，证明每日台账营业额与已确认公司结算收入精确对账；公司结算待到账不进入总收入，撤销到账确认后从开票月份扣除。
- 对经营日建立回归测试，证明营业和提前休息都计入经营日、休息不计入，经营日均台账营业额的分子分母一致。
- 对平均每车收入建立覆盖测试，证明只使用同时记录洗车数量的经营日、不包含公司结算、缺失不是零、洗车数量合计为零时不可用。
- 对称分解测试使用不同经营日数量和经营日均台账营业额组合，断言两个贡献精确相加为每日台账营业额变化，并且交换计算顺序不改变结果。
- 证据充分性测试覆盖 60% 默认阈值上下边界、关键数据缺失、任一期间无经营日、多个相近贡献和剩余未解释金额，断言后端状态而非模型自由措辞决定可用结论。
- 数据完整性测试覆盖未记录日期、部分天气、洗车数量覆盖率、分类合计不一致、无每日台账以及自定义范围，不把未记录日期解释为应营业日期。
- 单个 SQLite 快照测试在批量取证期间并发修改数据，验证一次 EvidenceBundle 不混合两个版本；临时 SQLite 故障只允许整批重试一次，第二次失败不保留部分证据。
- EvidencePlan 安全测试覆盖额外字段、SQL、表名、任意表达式、URL、门店/用户/角色/时区字段、超出白名单指标、多个分组、过量请求和越权修正。
- 计划修正测试证明仅格式、枚举或结构错误可以自动修正一次；权限、安全拒绝、含糊期间和未知分类不会通过重试或备用模型绕过。
- 模型失败测试覆盖临时超时、429、5xx、一次重试、备用模型完整阶段重做、无效密钥、余额不足、错误模型名、内容安全拒绝和全部供应商不可用；所有错误与告警必须脱敏。
- 会话测试覆盖每用户每门店一个当前对话、不同门店隔离、不同用户隔离、页面恢复、结构化状态、最近窗口、原始 Tool 证据保留、旧证据不自动复用、主动重置和永久删除。
- 重置测试证明聊天、结构化状态和原始 Tool 证据被删除，不含聊天内容的运行统计仍保留；重置前必须经过用户确认。
- 回答测试验证安全可读证据摘要、不显示原始 Tool JSON、准确日期和口径、覆盖限制、没有半截回答、没有未经后端证据支持的新金额。
- 白名单页面操作测试验证只接受开始月份和结束月份、后端拒绝 URL/门店 ID/未来或反向范围、前端只有用户点击后才按当前门店跳转。
- 主要前端验收 seam 是首页 Agent 对话区的用户可见交互。组件测试使用模拟 HTTP，验证角色可见性、发送问题、阶段状态、完整回答、错误、恢复、重置确认、门店切换和页面操作。
- Playwright 至少覆盖一个管理员端到端流程：选择门店、提问、看到证据回答、刷新页面恢复、点击“查看营业记录”预填范围、重置后旧消息消失。另覆盖普通用户看不到 Agent。
- 前端测试断言可访问名称、焦点顺序、状态区域、确认弹窗和响应式行为，不绑定 Tailwind 类名或组件私有状态。桌面和移动端都不得产生横向溢出。
- 公司结算回归测试必须在同一个启用公司结算的门店下覆盖普通用户、管理员和最终管理员的入口、页面、结算公司和开票记录访问，修复最终管理员缺失内容的问题。
- CI 只能使用 Fake Model Adapter，不能调用付费供应商或读取真实密钥。生产 Adapter 另用可丢弃原型和受控人工验证核对结构化输出行为。
- 发布评估集必须包含真实中文业务问法、金标准数值、权限攻击、提示注入、模糊日期、动态分类、数据缺失、格式错误、供应商故障、会话重置和白名单页面操作。
- 一票否决项为：任何跨门店或越权泄露、任何核心金额/期间/指标口径错误、把缺失当作零、编造证据、提示注入绕过、故障切换后改变权限或范围。语言质量、延迟和费用采用原型测得的阈值。
- 资源发布门槛在目标 2‑GB 服务器上测量空闲、普通业务和 Agent 请求峰值内存，并测量单请求延迟、受控并发、模型调用次数、Token、估算费用和 SQLite 快照持续时间。没有安全余量时不得开放功能。
- 优先复用现有认证、营业记录、公司结算、分析和首页测试形态。除确定性计算的极端边界外，不为内部辅助函数增加与实现耦合的浅层测试。

## Out of Scope

- 门店记忆、经营观察、事件类型、事件语义归纳、每周记忆刷新和记忆增强首页卡片。
- Agent 创建、修改或删除每日台账、公司结算或任何经营数据。
- 写操作提案、人工审批、LangGraph interrupt、一次性执行和 Agent 写审计。
- 跨门店查询、跨门店比较和管理员一次读取多个门店。
- 普通用户使用 Agent、普通用户月度配额和普通用户单独覆盖值；这些在后续开放普通用户时重新设计。
- 预测月底收入、未来收入、因果推断、自动经营决策和无证据经营建议。
- 按事件搜索、筛选、分组或解释多日规律；事件只在单日每日台账中原样展示。
- 任意 SQL Tool、任意数据库字段、任意文件/网络 Tool、任意 URL 跳转和模型生成路由。
- 动态 Skill 加载、`load_skill` Tool、多层 Skill 路由和开放式 ReAct 循环。
- LangGraph 产品级 checkpoint、LangGraph Server、LangSmith 强制依赖、独立 Agent 服务或独立 Agent 容器。
- 最终回答逐 Token 流式输出；是否增加流式输出由原型延迟决定。
- 在本规格中选定 DeepSeek、百炼或硅基流动的具体模型、主备顺序、精确超时秒数、Token 上限、每批请求数和默认结果行数。这些参数由原型测量后配置。
- 经营证据版本号、跨轮自动复用旧 Tool 证据和系统主动清理当前会话。
- 首页简报卡片的门店记忆提示、记忆刷新权限和记忆分类纠错界面。

## Further Notes

- 本规格取代历史 Phase 3 Agent 实施提案中与当前只读查询和经营分析冲突的内容。历史文件仍可作为背景，但不能照原文实现，尤其不能使用已失效模型名、跨门店管理员查询、Agent 写操作或独立 Agent 容器假设。
- 当前生产形态是单 FastAPI 进程、单 Uvicorn worker、SQLite WAL 与进程内短写锁。所有模型网络调用必须离开 SQLite 事务和写锁，批量证据读取必须保持一个只读快照。
- 领域词汇遵循项目 `CONTEXT.md`，使用“每日台账”“经营日”“记录天气”“平均每车收入”“月度总收入”“月度日均收入”“经营日均台账营业额”“经营分析”“公司结算”和“最终管理员”等规范名称。
- `CONTEXT.md` 当前包含访谈过程中产生的未提交术语修改；实现 Agent 时不得覆盖或回退这些用户已有修改。
- `.scratch/` 是用户已有未跟踪内容，不得修改、删除或纳入实现提交。
- 当前没有保存任何真实模型 API Key。原型评估时由用户在服务器安全配置中提供；聊天、Issue、Git 和示例配置中都不得出现真实密钥。
- 具体供应商和参数只有在结构化输出稳定性、失败语义、延迟、费用及 2‑GB 资源测试完成后才确定。实现必须保持可配置，避免业务代码依赖单一供应商。
- 该规格不要求在一个提交中完成。后续可以拆为小型实现工单，但拆分不得改变本规格的权限、数据口径、统一取证 Interface、安全失败和发布门槛。
