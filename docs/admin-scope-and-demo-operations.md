# 管理员范围升级与演示导入

Issue #279 的权限规则使用部署配置 `AUTOLAVA_BOOTSTRAP_USERNAME` 定位主管理员，优先于账号的原始 `role`。该账号始终能管理全部门店及员工，不能通过员工编辑授权取消这一能力。从管理员只能访问显式授权的门店；员工必须归属一个管理员，有效门店范围为自身与所属管理员范围的交集。

主管理员创建员工必须选择归属；从管理员创建员工自动归属自己。主管理员和员工创建者可以设置额外从管理员编辑授权。所属管理员保留员工编辑能力；创建者身份独立于当前归属，转移后仍可管理其创建的员工及编辑授权。额外编辑者只能编辑员工，不能转移归属、授予管理员身份、继续转授权或分配自己无权访问的门店。账号列表中的员工门店字段按操作者范围过滤，更新保留不可见的既有关系。

## 升级顺序

使用已有发布流程备份并验证现有 SQLite 文件，保留 `/data/autolava.sqlite3` 和 `/data/backups` 持久卷，不替换数据库。确认主管理员配置准确指向现有受保护账号。以下命令在后端工作目录执行；容器内使用相同模块命令。

```text
python -m alembic upgrade head
python -m app.scripts.create_admin
python -m app.scripts.initialize_permissions
```

结构迁移 0031 在升级时记录旧账号与旧门店快照，包含归档门店。权限初始化只执行一次，授予旧从管理员快照中的门店、保留旧员工门店关系并初始化归属和创建者为主管理员；配置主管理员本身不会被当作员工。缺少有效主管理员映射时初始化失败，不能启动对外服务；修正配置后重试同一快照。完成标记持久化，重启或重复执行不会恢复已收回的授权。空库可以先完成现有主管理员创建流程。

迁移 0032 兼容曾运行早期 0031 的本地数据库：早期版本只有员工归属，没有 `creator_id` 和 `employee_editors`，版本号相同导致 Alembic 不会重新执行更新后的 0031。0032 仅补齐缺失结构；对已完成初始化且原本没有创建者字段的员工，将当前所属管理员作为兼容创建者。这是旧库缺少创建历史时的兼容规则，不代表恢复了真实创建记录。既有完整 0031 的创建者和额外编辑授权保持原值；已收回的门店关系、初始化标记、密码及业务数据不变。降回 0031 时保留这两个属于最终 0031 的结构，不能借此恢复早期模型或清除授权。

Docker 启动命令、本地启动脚本和应用 lifespan 均保证对外服务前完成权限初始化。演示资料不会随启动自动导入。管理员降级或删除前必须先转移所属员工。收回从管理员门店范围会在同一事务中移除其员工对应关系并撤销会话；重新授权只恢复管理员自己的关系。

## 显式演示导入

权限初始化成功后，按现有部署方式配置 `AUTOLAVA_DATABASE_PATH` 指向需要增量导入的数据库，再执行：

```text
python -m app.scripts.initialize_demo
```

可选输入为 `AUTOLAVA_DEMO_USERNAME`、`AUTOLAVA_DEMO_STORE_NAME`、`AUTOLAVA_DEMO_PASSWORD`。默认账号名为 `demo-guest`，门店名为 `求职演示门店`。未提供密码时生成随机密码；提供时遵守现有密码规则。首次成功后命令向操作者输出一次凭据，应通过受控终端交付，不复制到代码、Issue 或常规构建日志。失败时不交付凭据。

导入在单一事务中创建一个演示门店、一个从管理员访客、仅该店授权、虚构台账、收入分类与覆盖样本月份的公司结算，并记录固定导入身份与版本。`AUTOLAVA_DEMO_DAYS` 默认 90，允许 90 至 3660 天。此项目发布时按用户要求设置为 731，覆盖至少两年的每日台账；不读取正式业务资料，不调用天气或模型服务，不复制正式数据或密钥。正常 AI 使用部署环境供应商配置。

模拟背景为意大利北部住宅与物流混合片区的自助洗车及车辆护理门店。样本体现周末客流、季节需求、模拟雨天、两年约 18% 的温和需求增长及日常波动；提前收工同时降低数量和收入，双月保养与节日休息归零，计数器漏报保留已清点金额。自助洗车按每次 7 欧元、车辆护理按每次 24 欧元生成，设备计数不计入营业额。两家虚构车队逐月开票，历史账款已确认，近期保留待到账；这些规则为人为演示设定，不是实际天气、因果证据或经营预测。有效旧登记仍保持原样，不因本次样本规律调整重建。

后续获授权更新服务器时，最终使用原主数据库与独立演示门店：先备份原库并在隔离副本验证升级和两年导入，再在原库完成权限初始化，设置 `AUTOLAVA_DEMO_DAYS=731` 执行增量演示导入。保留正式数据和账号，通过门店范围隔离访客。不要将两份 SQLite 表按原始数字 ID 拼接，也不要用额外验证库替换原库。额外验证库用于验收和留档，服务器中的演示业务对象由导入命令重新分配 ID。若原库已有有效导入登记，重复命令会保留现有样本而不会扩展为两年，须先评估已有登记和体验修改，不能删除登记强制重建。

重复导入保留所有体验修改、密码及授权，不补数据、不重新输出凭据。账号或门店名称冲突、与主管理员同名、登记版本不兼容、引用缺失或中途失败均整体拒绝；不认领已有对象、不自动修复或重建。并发运行最多创建一套。遇到登记损坏应先核对备份与现状，不删除标记来强制重新导入。

## 发布前验证

在隔离旧库副本先验证升级、重复初始化及显式演示导入。登录主管理员核对全部范围，登录访客核对仅演示店；直接请求其他门店的业务、导出、管理及 AI 接口应失败。验证记账保存和刷新、公司结算确认/撤销的月度收入变化、员工创建和真实登录，以及撤权后旧会话和后台 AI 任务被拒绝。

生产数据库操作、真实访客凭据交付、镜像部署和 HTTPS 验收是独立发布步骤。本实现会话未执行这些步骤；本地受控模型验收不能证明真实模型供应商或生产 HTTPS 已通过。
